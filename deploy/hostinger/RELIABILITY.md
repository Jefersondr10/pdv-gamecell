# Reliability release, September 2026

## Guarantees and limits

- Sale/entry drafts, including Files, are stored in IndexedDB scoped by store and user. Before sending, an immutable operation envelope is durably saved. Its UUID is both the idempotency identity and the server record ID. A retry first queries the authenticated operation endpoint. A lost response is not displayed as success until server confirmation.
- A persistent cross-tab lease prevents duplicate upload work. SQL transactions and immutable operation IDs provide final protection. Conflicting drafts are blocked rather than silently overwritten. Storage failure before transmission blocks sending.
- This is interruption recovery, not full offline inventory. Resume on reopening the same browser/profile and signing into the same shop/user. Clearing browser data, uninstalling, device loss, or unfinished local writes can lose unsent work. Photos must finish uploading before the server can read them.
- Receipt processing is a durable SQLite job queue. The server works after the browser closes. OCR has its own internal-only, resource-limited container, no production data volume, no credentials and no Internet network. Manual corrections and cancellation take priority through generation/lease comparisons.
- OCR compares document amounts; it never proves that a bank transfer actually settled. Unreadable files or exhausted retries require explicit review. HEIF containers with multiple images deliberately require manual review.

## Release procedure

1. Pass the recovery, queue, migration, backup, baseline and integration tests on synthetic data. Test both PDF and image through the real engine. Build immutable application and OCR images from the same reviewed source revision.
2. Run the application candidate with a separate synthetic database and private OCR network. Require both health checks, authentication, operation lookup, receipt upload and persisted completion. Do not run data-creating integration tests against the public site.
3. Build images with the label `org.opencontainers.image.revision=FULL_COMMIT_SHA`. The original `deploy-reliability.sh` is a historical procedure for the 0009 release, not a current release entrypoint. For the incremental backup-settings release on an already healthy 0009 installation, execute `sh scripts/hostinger/deploy-backup-settings.sh TAG EXPECTED_OLD_TAG FULL_COMMIT_SHA`. It verifies the exact live image/mount and new source label, checks an already completed scheduled backup is recent, makes an on-server SQLite safety copy, applies additive migration 0010 and switches only the application. It never initiates an external backup, changes OCR configuration or changes backup destinations. Failures after the switch restore the previous application configuration. Never reuse the old ranking-only deployment script.
4. Migrations are not auto-applied on app startup. The health endpoint requires both `receipt_ocr_jobs` and `store_backup_alert_settings`. The dedicated runners are `apply-receipt-migration.mjs` (0009) and `apply-backup-alert-migration.mjs` (0010, requires the existing release ledger). Do not replay migrations 0000–0008 against production: some are historical seeds/reset gates. Runners validate schema/checksums and preserve business data. Repeated invocations create additional on-server pre-migration copies; keep them until release verification, then use an explicitly scoped retention procedure.
5. Run `npm run build:sites` before the Sites `package-site.sh` helper. The helper packages existing output; never feed it the VPS build output. Verify the Worker default export contains `fetch`, then save and publish the revision to the existing Sites project with migration read-only/proxy settings unchanged. A saved version is immutable/deduplicated by source revision: after a packaging failure, register a new corrected source revision instead of retrying the failed version. Sites remains the encrypted off-site backup destination, not a second writable inventory database.
6. Observe the next already scheduled backup and verify accepted remote health; a deployment does not independently authorize a new external data transfer. Confirm recovery clients and server OCR without changing real sales. Retain previous image/configuration; an application rollback retains the additive schema and all current business records.

## Backup monitoring

The owner/admin UI reports unknown, healthy, warning after 90 minutes, late after 150 minutes, or last-attempt failure. It exposes no encryption keys, backup identifiers or private file paths. A successful status means remote upload completed, not that each backup has been restore-tested.

Sites maintains a receipt timestamp only after accepting a new encrypted snapshot. `GET /api/system/vps-backup?health=1` uses a separate `VPS_BACKUP_MONITOR_TOKEN` and returns only healthy/unhealthy. This monitor credential cannot list or download backups. Replaying an old snapshot cannot refresh the timestamp.

**External notification delivery is not active yet.** It requires the owner's actual destination and an external monitor configured outside the VPS (so total VPS downtime also alerts). Do not label alerts active merely because the protected endpoint exists. Monitor every 5 minutes, notify after two consecutive failures and on recovery; test stale backup, endpoint failure and delivery before activation. Keep encryption recovery keys separately from the VPS and periodically restore to an isolated directory.

Owners can save, replace or remove their shop's destination in **Ajustes › Sistema › Alertas de backup por e-mail**. This is separate from their login address and is never seeded across shops. The owner-only API uses CSRF protection, optimistic revision checks and atomic auditing without duplicating the address in audit details. Saving a destination does not send or verify mail: both API and UI explicitly report automatic delivery as not configured. A future external monitor must retain only the minimal destination configuration it needs outside the VPS, use separate credentials, and confirm delivery before this status changes.

The incremental release temporarily pauses the backup timer while replacing the application and resumes it on every exit; it aborts without touching any already running backup service. It verifies the exact new image and data mount after switching. If migration fails before the switch, the app stays unchanged and the saved pre-release configuration is deliberately retained; inspect that failure before choosing a fresh release tag or explicitly authorizing removal of that one checkpoint file.
